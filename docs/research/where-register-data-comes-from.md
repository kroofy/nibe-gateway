# Where the register data comes from

Written 2026-10-25 in answer to the owner's question: "Are all these registers coming from the pump? Does the
NIBE broadcast them, or is this a list of things found in third-party sources?"

Labels: **VERIFIED** = seen in our code, our captures or on the owner's F730. **SOURCE** = taken from
third-party documentation or code, not checked on this pump. **HYPOTHESIS** = our best guess.

## Short answer

The list of 581 registers is a **dictionary taken from third-party sources**: NIBE's own ModbusManager export
for the F730 and the NibePi project. The pump never sent us that list. On the wire, the pump only **offers
turns**. Every value we show exists because the gateway asked the pump for that one register and the pump
answered. The pump sends nothing on its own that contains register values (its "data" frames are empty because
no LOG.SET file is configured). Of the 581 registers, **31 have been read from your F730 with real values**
(the 30 polled ones plus 45171), with 0 timeouts. Two writes are hardware-verified, 47011 heat offset and 45171
alarm reset. The other 550 registers are listed but have never been read, so they stay "unverified".

## 1. The catalog is a dictionary from third parties

`fixtures/register-catalogs/f730.json` has **581 entries** (not 1000+). It is generated by
`docs/research/tools/build_f730_catalog.py`; provenance is in `docs/research/register-catalog.md` §1 and.
The counts below come from running Python over the file (VERIFIED).

| Source (`sources` key) | What it is | Entries citing it |
|---|---|---|
| `nibepi-f730` | anerdins/nibepi `models/F730.json` (MIT), the file the owner's old NibePi used | 578 |
| `nibe-modbusmanager-f730-db8310` | NIBE ModbusManager 1.0.9 CSV export, "Product: F730", DB 8310, 2020-06-24 (via yozik04/nibe) | 576 |
| `yozik04-nibe-extensions` | yozik04/nibe community corrections (GPL, only facts referenced) | 2 as sole source, plus 13 conflicts |

- 575 entries are in both NibePi and ModbusManager. The two agree on type, scale, access and min/max for all 575
  (`register-catalog.md` §1). Three are only in NibePi (43110, 43111, 47260), one is only in ModbusManager (47340), and
  two come only from the community list (48852 word swap, 48889 disable LOG.SET).
- **13 entries carry `conflicts`**: places where the community list disagrees. The disagreement is recorded but
  the correction is not applied. Examples: 40051 scale 100 vs 10, 43141/43375 W vs kW, 47377 u8 vs s16.
- 309 entries are `read` and 272 are `read_write`. "read_write" is only what the source **claims**.
  `write_allowed` is `false` on all 581.
- **All 581 have `verification: "unverified"`**, by design (`f730.json` `semantics.verification`). Results from
  the hardware go in a separate overlay for each installation. The shared file is never edited.

So, in effect, the catalog is the manufacturer's register list (SOURCE). It tells us how to decode a number
(type, scale, unit). It does **not** tell us whether this F730's firmware (product-info version 9721) supports a given register.

## 2. How data actually flows on the wire (MODBUS40 accessory mode)

The pump is the bus master. The gateway acts as the "MODBUS40" accessory at address 0x20 and may only speak when
the pump gives it a turn. The frame types are listed in `docs/research/protocol.md` §4. What the owner's F730 actually
sends was captured passively on 2026-10-24 (`fixtures/serial-captures/real-f730-passive-2026-10-24.capture.jsonl`,
replayed in `crates/device-f730/tests/replay.rs`; HARDWARE_PENDING.md line 68). VERIFIED.

| Frame | Direction | What happens | Seen on the owner's F730 |
|---|---|---|---|
| 0x69 read token | pump → us | "Your turn to read." We send one read request `C0 69 02 <reg LE> <xor>` for one register, or just ACK (`crates/protocol/src/lib.rs:72` `read_request`, `:113` `reply`) | every ~1.0 s |
| 0x6A read response | pump → us | Register number + 4 value bytes; we ACK and decode it with the catalog's type and scale | only after we ask |
| 0x6B write token / 0x6C write response | pump → us | "Your turn to write." We send a write only if a gated write is queued (`runtime.rs:703`, `writes.rs`). Otherwise we ACK. 0x6C = 1 accepted / 0 denied | token every ~1.0 s |
| 0x68 data message | pump → us | Unrequested push of up to 20 registers chosen by a **LOG.SET** file (USB stick, NIBE ModbusManager) | every ~2–3 s, **always empty** |
| 0x6D product info | pump → us | Model string + version: `F730 Cu 3x400V`, version 9721 | every ~6 s (~15 s once we ACK) |
| 0xEE version request | pump → us | Accessory version query; we ACK it, as NibePi does | every ~1.5 s (~4.7 s once we ACK) |

**Is anything broadcast without asking?** Yes, but nothing useful. The pump sends tokens, product info, 0xEE
and 0x68 data frames without being asked. The 0x68 frames are the only place where register values could arrive
unasked, and on this pump they are empty because no LOG.SET is configured (VERIFIED). We did not set one
up because it requires a USB stick and the ModbusManager tool at the pump, it caps out at about 20 registers, and
read requests already give us everything. Live values therefore come from **polling**: the
gateway cycles through `poll_registers`, one register per read token (`discovery.rs:39`, `MIN_PROBE_INTERVAL_MS = 800`).
30 registers at about 1 per second gives a full refresh about every 30 s.

## 3. What has actually been read from the owner's F730

The 30 `poll_registers` in `packaging/raspberry-pi/stage-nibe/00-install/files/hardware.json` were checked
against the live device on 2026-10-25 with
`GET http://nibe-gateway.local:8080/api/v1/registers/explorer` (read-only) (VERIFIED):

- **31 registers are `confirmed-readable`** with source `NIBE 0x6A`: the 30 polled ones plus 45171 (read
  back after the alarm reset). The other **550 are `unverified`** (never asked), and **0 are `unsupported`**.
- Poll counters: 1760 reads, **0 timeouts**, 58 complete error-free rounds. Wire: 0 checksum errors, 0 NAKs,
  0 reply-deadline misses.
- Sample live values: outdoor 40004 10.2 °C, room 40033 20.9 °C, hot water top 40013 48.4 °C, compressor
  43136 34.9 Hz, 47265 exhaust fan normal 55 %, 47011 heat offset −2, 48852 word swap 0, alarms 45001 = 0.
- Other one-off probes (HARDWARE_PENDING.md line 76): 41256–41258 and 43108 "fan speed current" all read 0 %.
  42075 (EME20, not fitted) returned the "no value" sentinel. This shows that "the pump answers" does not
  always mean "the register is meaningful on this unit".

**Decoding checked against the pump display / myUplink** (2026-10-24 ~20:45, HARDWARE_PENDING.md line 76,
VERIFIED by the owner): indoor 20.7 = 40033 20.7–20.8 °C; hot water 41→42 °C = 40013 41.5–41.6 °C; outdoor
10.1 ≈ 40004 10.0 °C; ventilation 55 % = 47265 55 %; heat offset −2 and the alarm matched too.
**Correction:** the myUplink "energy log 3949 kWh" did **not** match a register. It is a period total. The
registers 41846/41848/41850 hold lifetime totals (≈1972 / 10184 / 19965 kWh). Those are plausible, but no
display figure has confirmed them. Word order (48852 = 0, high word first) is VERIFIED: 48852 was read directly, and the
42075 sentinel `FF FF 00 80` decodes as −32768 only in that order.

## 4. What "verified" means here, and the risks

- **Read verified** (`confirmed-readable`) means the pump answered a read for this register with a plausible,
  non-sentinel value (`register-catalog.md` §3). This shows the register exists and that the type and scale
  give a believable number. It does not by itself prove the meaning. Only the handful of values cross-checked
  against the display are proven that far.
- **Write verified** means one specific register was written once on hardware with the owner watching. The
  pump accepted it (0x6C), the read-back matched, and myUplink showed the change. Done for **47011 heat offset**
  (HP-27) and **45171 alarm reset** (HP-28, refined as a 0→1 edge in HP-31). **48132 Temporary Lux** is
  readable (reads 0) but its write is **pending HP-32**. Only 47011 is in `writable_registers`. There is no raw
  write endpoint (`capabilities.raw_writes: false`).
- The catalog keeps every entry `unverified` because hardware results live in the overlay for each installation.

Risks of relying on third-party lists (SOURCE/HYPOTHESIS until a register is read on this pump):
- Wrong **scale, unit or type**. The 13 recorded conflicts show the sources already disagree, for example 43141 W vs kW.
- Wrong **32-bit word order**. This is settled for this pump (48852 = 0), but the sources conflict on how 0x68 frames are handled.
- Registers that are listed but **not present or meaningful** on this firmware (9721) or this unit's
  accessories, such as 42075 EME20 (sentinel) and the fan-speed-current registers (always 0). The catalog has no firmware ranges
  (`f730.json` `firmware.applies_to: "unknown"`).
- "read_write" in a source does not mean a write is safe or has any effect. This is why each write needs its own hardware test.
